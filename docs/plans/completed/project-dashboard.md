# Design Plan — Read-Only Project Dashboard

Status: Completed — pending final review and merge

## Problem

Swing Trader now has strong repository-native state: experiment and knowledge registries, a preregistered prospective protocol, durable operational/prospective archive workflows, and explicit validation boundaries. That state is reviewable but fragmented across Markdown, YAML/JSON, GitHub Actions, and Releases. There is no single human-facing cockpit for understanding project status without reading the repository directly.

## Goals

- Build a read-only web dashboard derived from canonical repository records rather than creating a second source of truth.
- Make the most important research status impossible to misread: frozen strategy v1, **NOT VALIDATED**, research-only/no deployment claim, and the prospective validation gates.
- Summarize historical experiments from `experiments/registry.json` without reinterpreting them into a new research verdict.
- Summarize the source-governed knowledge layer from `knowledge/registry.json`, including source/note/news counts and topic coverage.
- Show configured universe and benchmark metadata from `config/universe.yaml`.
- Enrich the static site with optional live GitHub metadata for open PRs, recent Actions status, daily scan archive status, and prospective holdout archive status.
- Degrade gracefully when GitHub API calls fail or are rate-limited; canonical research status must remain visible offline.
- Publish the static site through GitHub Pages when repository Pages is configured for GitHub Actions.
- Keep the site accessible, responsive, dependency-light, and usable on mobile.

## Non-goals

- No order placement, broker/exchange controls, or strategy/risk mutation from the UI.
- No editing of knowledge, experiments, config, or project state through the dashboard.
- No user authentication, database, backend server, or external analytics service in v1.
- No live market-data feed, charting of unverified PnL, or reconstruction of missing prospective evidence.
- No interpretation of daily scan history as prospective validation.
- No Notion synchronization in this milestone; GitHub remains the canonical source and the dashboard is the primary presentation layer.

## Architecture

Use a two-layer static site:

1. **Deterministic build layer** — Python reads canonical repository files and emits `project.json` plus copied static assets into an output directory. Given fixed repository inputs and repository name, generated bytes are deterministic and contain no build timestamp.
2. **Optional live enrichment layer** — browser JavaScript calls the public GitHub REST API for non-authoritative operational metadata such as open PR count, recent Actions status, and yearly Release asset dates. Failures render `Unavailable` without changing canonical status cards.

Source layout:

```text
dashboard/
  index.html
  styles.css
  app.js
src/swing_trader/
  project_dashboard.py
  project_dashboard_cli.py
tests/
  test_project_dashboard.py
.github/workflows/
  project-dashboard.yml
```

Generated output is not committed. The workflow builds it into `.artifacts/project-dashboard/site/`, validates it, uploads an ordinary workflow artifact on pull requests, and uploads a GitHub Pages artifact on `main`/manual/scheduled runs.

## Canonical dashboard model

`project.json` schema v1 should include only mechanically recoverable facts:

- repository identity;
- strategy version/status and fixed research-only / not-validated labels;
- historical experiment id/name/stage/decision/directory;
- prospective protocol id/status/strategy version/start/minimum end/minimum closed trades;
- knowledge source/note/news counts and topic frequencies;
- configured assets and benchmarks;
- operational archive tag prefixes used for live lookup;
- explicit evidence-boundary copy explaining that operational/news context is not holdout evidence.

Do not derive a pass/fail validation verdict from retrospective experiment decisions. `validation_status` remains `not_validated` until a future reviewed project change explicitly changes the canonical research state after the prospective gates mature.

## UI

Single-page dashboard sections:

- **Status hero** — strategy v1 frozen, research-only, NOT VALIDATED.
- **Prospective validation** — start date, minimum end date, 30-closed-trade gate, live latest archive date/count when available.
- **Operations** — current main/CI/open-PR metadata, daily scan history latest archive date/count when available.
- **Experiments** — EXP-0001 through EXP-0006 with stage and recorded decision.
- **Knowledge** — source/note/news counts and topic coverage; news count can remain zero before ingestion exists.
- **Universe** — configured assets and benchmarks.
- **Evidence boundaries / next steps** — concise rules from canonical architecture/roadmap intent without creating a new decision store.

Use semantic HTML, visible focus states, sufficient contrast, responsive grid layout, `prefers-reduced-motion`, and no external font/JS/CSS dependencies.

## Live GitHub enrichment

Client-side requests are best-effort and read-only against the public repository:

- repository metadata;
- open pull requests;
- recent Actions workflow runs on `main`;
- current-year `daily-scan-history-YYYY` Release;
- current-year `prospective-v1-holdout-data-YYYY` Release.

When a release exists, parse only known canonical asset filename prefixes/dates. Missing releases are valid states, especially before the first prospective observation. Do not fetch archive contents or compute signals/PnL in the browser.

## GitHub Pages workflow

Use the current GitHub Pages Actions pattern:

- `actions/checkout@v6`;
- `actions/configure-pages@v5`;
- `actions/upload-pages-artifact@v4`;
- `actions/deploy-pages@v4`.

Pull requests run a read-only build/test/artifact path and never deploy. `push` to `main`, daily schedule, and manual dispatch may deploy. Deployment requires `pages: write` and `id-token: write` only in the deploy job/environment.

GitHub requires Pages to be configured to use GitHub Actions. If that repository-level setting is not already enabled, the build remains valid and deployment may require the one-time repository setting; do not weaken CI or use a second hosting source as a workaround.

## Validation

- deterministic `project.json` and site assets for fixed input fixtures;
- exact strategy status remains `not_validated` regardless of retrospective experiment decisions;
- prospective gate fields match the experiment registry;
- knowledge counts/topics match the knowledge registry;
- universe symbols/benchmarks match `config/universe.yaml`;
- generated site contains no external script/style dependencies;
- JavaScript live layer has explicit loading/unavailable states and does not overwrite canonical validation labels;
- builder rejects repository/template output paths and unrelated output entries rather than overwriting them;
- `pytest -q` passes with 129 tests;
- `ruff check src tests` passes;
- the initial PR workflow build passed without deployment; final-head checks remain required before merge;
- final diff-based review and merge remain required.

## Simplify

The implementation uses plain HTML/CSS/vanilla JavaScript and a small Python snapshot builder rather than a frontend framework, server, database, or dashboard SaaS. Live GitHub status remains outside canonical `project.json`; the build also fails safely when an output path could overwrite source/template content or contains unrelated files.

## Compound
