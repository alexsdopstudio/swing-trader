# Separate Canonical State from Live Dashboard Enrichment

## Problem

A project dashboard needs to show current operational information without allowing transient API responses to become an unofficial source of truth for research status or validation claims.

## Symptoms

- A page becomes unusable when a live API is rate-limited or unavailable.
- Browser code derives or overwrites a validation verdict from recent workflow, Release, or pull-request data.
- Time-varying API fields are embedded in a committed or reproducible project snapshot.
- The UI implies that operational archives, news, or an empty release list prove or disprove a prospective validation gate.

## Root cause

Authoritative research records and live operational metadata have different update cadence, provenance, availability, and inference boundaries. Treating them as one data source makes the dashboard nondeterministic and can elevate presentation state into evidence.

## Reusable solution

Build a deterministic static snapshot from canonical repository records first. Encode immutable research labels and evidence-boundary copy in that snapshot. Then load public operational metadata in the browser as an optional, read-only enhancement that has its own loading and unavailable states.

Keep the live layer unable to write canonical labels, source records, experiment records, strategy/risk settings, or holdout conclusions. Missing data should render an explicit unavailable state while the canonical snapshot remains usable.

## When this applies

Use this pattern for static dashboards, reports, or documentation sites that combine version-controlled project records with changing CI, repository, release, status, or news metadata.

## When this does not apply

Do not use a client-side public API as a substitute for an authenticated operational control plane. A dashboard that needs to change project state, access non-public data, or make trading decisions requires separate authorization and safety design.

## Tests and checks

- Assert that fixed validation and deployment labels originate only from the canonical snapshot.
- Build twice from fixed repository inputs and compare generated bytes.
- Verify that no external script, stylesheet, font, or framework dependency is required for canonical rendering.
- Exercise unavailable and partial live-data states without hiding canonical research status.
- Keep build outputs isolated from source/template directories and reject unexpected output contents.
